# Developer runbook: connect Zoho Mail to Cloudflare DNS

Use this runbook after Evans has created the Zoho organization and added `rhemarealestates.com`. Evans owns the Zoho account. The developer's task is limited to the DNS values Evans shares from Zoho Admin Console and verifying the result.

## Roles and boundaries

**Evans**

- Owns the Zoho organization, mailbox, recovery details, and password.
- Adds the domain and creates `evans@rhemarealestates.com`.
- Copies the DNS records generated by his Zoho account and shares them with the developer.
- Decides whether and when to move existing email service to Zoho.

**Developer**

- Uses their own Cloudflare login that Evans authorized. Never ask for Evans's password or MFA code.
- Reviews the current DNS and existing mail setup before editing.
- Adds only the approved Zoho verification, MX, SPF, and DKIM records.
- Tells Evans when to verify the records in Zoho and helps test mail delivery.

Do not create a Zoho account on Evans's behalf, accept a paid plan, change nameservers, or change website records as part of this task.
If your Cloudflare access does not permit DNS editing, ask Evans to grant the minimum DNS-edit permission for this zone. Do not use his login.

## Before changing DNS

1. Sign in to Cloudflare using your own authorized account.
2. Open the `rhemarealestates.com` zone and confirm Cloudflare shows it as active. If it is not active or you are unsure Cloudflare is authoritative for DNS, stop and ask Evans. Do not change nameservers.
3. Go to **DNS** > **Records**. Review the existing `A`, `AAAA`, `CNAME`, `MX`, and TXT records before making changes.
4. Record the current MX and SPF TXT values in a private change record so they can be restored if the email migration needs to be reversed. Do not put DNS snapshots, credentials, or tokens in Git or public project documents.
5. Ask Evans whether anyone currently uses an email address at `@rhemarealestates.com`. If the answer is unknown or another provider is in use, do not replace MX records yet. Agree on the migration timing first.
6. Ask Evans to send the exact DNS details shown in his Zoho Admin Console. For each record, you need its type, name/host, value/target, and priority if it is an MX record. Do not use records copied from a generic example.

Cloudflare notes that domains managed through a hosting partner may need DNS changes made through that partner instead. If Cloudflare does not control the active DNS, stop and identify the authoritative provider with Evans.

## Add Zoho's domain verification record

1. In Cloudflare, open **DNS** > **Records** for `rhemarealestates.com`.
2. Select **Add record** and choose the exact type Zoho generated, usually TXT or CNAME.
3. Enter the exact **Name** and **Content/Target** Zoho shows. Use the root name (`@`) only if that is what Zoho specifies.
4. Leave TTL at **Auto**, unless Zoho's instructions require otherwise.
5. If Zoho supplied a CNAME and Cloudflare offers a proxy toggle, set it to **DNS only**. TXT records are not proxied.
6. Save the record and tell Evans it is ready for verification in Zoho.

Do not edit an existing website CNAME to make room for this record. If the Zoho record conflicts with an existing record at the same name, stop and resolve the conflict with Evans before proceeding.

## Create the mailbox before switching MX

Confirm Evans has created `evans@rhemarealestates.com` in Zoho before changing MX. If another mail provider is active, agree on the switch with Evans first. MX records direct incoming mail for the whole domain, not only Evans's address.

When Evans approves the switch:

1. Open the domain's MX setup in Zoho Admin Console and use the exact MX hosts and priorities shown there.
2. In Cloudflare **DNS** > **Records**, add all required Zoho MX records.
3. Remove or replace previous MX records only if the agreed migration requires it. Do not leave old provider MX records in place as an assumed backup; they can route mail unexpectedly.
4. Do not alter website `A`, `AAAA`, or `CNAME` records, nameservers, or unrelated TXT records.
5. Save and ask Evans to verify MX in Zoho. If Zoho does not verify immediately, allow time for DNS propagation before troubleshooting.

Zoho's MX values can vary by data center. Use only the values in Evans's Admin Console.

## Add SPF and DKIM

### SPF

1. Find any existing SPF TXT record for the domain before adding one.
2. Ask Evans whether any other service sends email as `@rhemarealestates.com`, including website forms, marketing tools, or an older provider.
3. Use the exact Zoho SPF guidance, but maintain only one SPF record for the domain. If one already exists, merge the approved sending services into that record instead of adding a second SPF TXT record.
4. If you cannot determine which senders are still in use, do not replace the record. Ask Evans.
5. Save the record and ask Evans to verify SPF in Zoho.

### DKIM

1. Ask Evans to generate a DKIM selector in Zoho Admin Console.
2. Add the exact TXT name and value shown by Zoho.
3. Save the record and ask Evans to verify the selector and enable it in Zoho.

Do not invent or reuse SPF/DKIM values from another account. Keep existing mail authentication records until the responsible sender and migration are understood.

## Verify and test

1. Confirm Zoho shows domain ownership, MX, SPF, and DKIM as verified.
2. Have Evans sign in to Zoho Mail and send a message to an outside address he controls.
3. Reply from that address and confirm it arrives in Zoho.
4. Send a new message from the outside account to `evans@rhemarealestates.com` and confirm delivery.
5. Confirm the Rhema website still resolves and its existing website DNS records were not changed.
6. Tell Evans which records were added or changed and whether both send and receive tests passed.

If receiving fails, recheck MX records and wait for propagation. Compare with the pre-change values you recorded. Restore prior MX only after coordinating with Evans, since that sends incoming mail back to the previous provider.

## Separate website email work

Finishing these DNS steps creates a mailbox. It does not enable application email.

- **Supabase Auth:** Phase 08 requires a production SMTP provider for password recovery and other Auth emails. Supabase says its default SMTP is restricted to pre-authorized team addresses and currently limited to 2 messages per hour, so it is not production-ready. Zoho's Free plan listing excludes IMAP/POP/ActiveSync and does not establish that the account supports the authenticated SMTP connection Supabase needs. Confirm SMTP access and terms with Zoho first. If unavailable, Evans must approve a separate SMTP provider before the developer configures it.
- **Website inquiries:** The inquiry form does not automatically email the mailbox. Phase 07 does not include email sending. Production inquiry submission also depends on the Vercel Production environment variables recorded in `docs/progress.md`; completing that setup stores inquiries for the admin workflow, it does not create inbox notifications.
- **Website administrator access:** Provisioning Evans as a website administrator is a separate trusted Supabase process. A Zoho mailbox does not grant application access.

Do not paste mail passwords, SMTP credentials, Supabase secrets, or verification codes into Git, these documents, or chat. Configure any approved service credentials only in the appropriate protected dashboard.
